# Play-by-Play Archive (1996-97 → 2025-26) — Design

Date: 2026-07-31
Status: Approved for implementation planning

## Goal

Acquire and preserve the complete NBA event-level play-by-play history for
every regular-season, playoff, and play-in game from 1996-97 through 2025-26
(approximately 38,500 games and 18 million events). Publish it as a validated,
season-partitioned Parquet dataset backed by exact raw JSON, deterministic
manifests, and verified NAS recovery.

The archive supports:

1. COVID home-court analysis of foul timing, clutch periods, scoring runs,
   and timeouts;
2. reproducible pace, clutch, and garbage-time features in later modeling
   work; and
3. durable preservation of the complete source responses while they remain
   available.

Derived analytical features are regenerated by later code. They do not enter
the archival table.

## Verified source evidence

Live source probes on 2026-07-31 established:

- `PlayByPlayV3` returns event logs for the first scoped regular-season and
  playoff games as well as modern regular-season and play-in games.
- The V3 response has an outer `gameId` plus the same 23 action fields across
  the representative responses.
- `actionNumber` is not unique and is not monotonic. `actionId` is unique and
  strictly increasing in response order.
- Early responses use string `"0"`/`"0"` as a non-scoring sentinel after the
  game has a nonzero score. Modern responses use empty strings for the same
  condition. Neither raw score pair is a running score on every row.
- Representative responses were:

| Game | Class | Actions | Periods | Terminal score |
|---|---|---:|---|---|
| `0029600001` | first scoped regular season | 500 | 1–4 | home 98, away 107 |
| `0049600001` | first scoped playoffs | 404 | 1–4 | home 109, away 99 |
| `0051900111` | special 2020 play-in | 510 | 1–4 | home 126, away 122 |
| `0022500001` | modern double overtime | 611 | 1–6 | home 125, away 124 |

`LeagueGameFinder` independently returned:

- 1,189 regular-season games and 72 playoff games for 1996-97;
- one play-in game for 2019-20; and
- six play-in games for 2020-21.

The 1,189-game 1996-97 regular-season set agrees with the existing
`games.parquet`. Existing pinned hoopR evidence also confirms one 2020 play-in
game and six games in each 2021–2026 play-in tournament.

## Scope and sequencing

This is one implementation project with three connected stages:

1. acquire and validate exact worklists and raw play-by-play responses;
2. normalize and publish one deterministic archival dataset; and
3. create and restore-verify one immutable raw-plus-Parquet NAS snapshot.

Implementation starts only after the reviewed `playoff-game-results` branch is
integrated. That publication supplies:

- exact postseason results and counts for cross-validation;
- the canonical `play_in` spelling;
- shared transactional publication infrastructure; and
- established archive, restore, manifest, and provenance patterns.

This sequencing is an execution precondition, not permission to merge either
branch. Implementation ends on an unmerged branch ready for separate review.
It is not pushed, merged, deployed, or torn down without explicit direction.

## Source and dependency decisions

| Decision | Choice |
|---|---|
| Play-by-play source | `nba_api` `PlayByPlayV3` exclusively |
| Worklist source | `nba_api` `LeagueGameFinder` |
| Game types | `regular`, `playoff`, and `play_in` only |
| Ending seasons | integers `1997..2026` |
| Publication | fixed archival Parquet projection plus exact raw JSON |
| Storage | gitignored `data/raw/stats_nba/pbp/` and `data/parquet-large/pbp/` |
| Recovery | one immutable, checksummed raw-plus-Parquet NAS snapshot |
| Committed products | code, tests/fixtures, documentation, and audit report only |

Preseason, All-Star, tiebreaker, voided, exhibition, and live/in-progress games
are outside this archive. Pre-1996 play-by-play does not exist at the source.

## Components

```text
src/nba_data/pbp.py
    Worklist acquisition and normalization
    Exact worklist and per-game cache validation
    Serialized PlayByPlayV3 fetching and bounded retries

src/nba_data/pbp_build.py
    Fixed-schema event normalization
    Running-score derivation
    Whole-archive validation
    Deterministic partitions, manifest, and audit data

src/nba_data/publication.py
    Existing pair publication
    New transactional tree publication used by the PBP dataset

scripts/archive_pbp_snapshot.sh
scripts/restore_pbp_snapshot.sh
    Exact immutable snapshot and absent-target recovery
```

The source module performs no Parquet publication. The builder performs no
network access. Archive scripts consume only a complete, validated raw cache
and publication.

## CLI

The source-checkout CLI adds:

```text
python -m nba_data fetch-pbp --season 2026
python -m nba_data fetch-pbp
python -m nba_data build-pbp
```

`--season` uses the repository's ending-season integer convention and accepts
`1997..2026`. `fetch-pbp` is the only network path. It acquires or resumes one
closed season or the full archive. `build-pbp` is a complete offline rebuild
from verified caches; a partial publication mode is intentionally omitted.

Extending the range to 2026-27 or ingesting an active season requires a
separately reviewed design change.

## Worklist acquisition and validation

There are 67 exact worklist responses:

- Regular Season for every ending season `1997..2026`;
- Playoffs for every ending season `1997..2026`; and
- PlayIn for ending seasons `2020..2026`.

Each response is cached at:

```text
data/raw/stats_nba/pbp/worklists/<season>/<game_type>.json
data/raw/stats_nba/pbp/worklists/<season>/<game_type>.json.meta.json
```

All 67 responses are fetched into the dedicated PBP worklist tree. The
existing `data/raw/stats_nba/leaguegamefinder_<season>.json` sidecars are not
seed sources because they predate exact request-parameter metadata. They
remain untouched. Seven additional 2020–2026 regular-season requests are
negligible compared with the full archive and give every PBP worklist the same
complete provenance contract.

Every LeagueGameFinder game must have exactly two team rows. The normalizer
produces one deterministic row with:

```text
game_id, season, game_type, game_date,
away_franchise_id, home_franchise_id, away_pts, home_pts
```

The complete normalized worklist must satisfy all of these gates before the
first PBP request:

1. `game_id` is a ten-character string and is globally unique.
2. Prefixes are exactly `002` for `regular`, `004` for `playoff`, and `005`
   for `play_in`.
3. The ID prefix agrees with the season-type request that returned the row.
4. The same ID does not appear in two season-type responses.
5. Dates, franchises, and nonnegative integer final scores are complete.
6. Every regular-season row equals `games.parquet` in both directions on
   game ID, date, franchises, and scores.
7. Every playoff and play-in row equals the integrated
   `playoff_games.parquet` subset in both directions on season, date, type,
   franchises, and scores. Basketball Reference game IDs are not compared.
8. The special 2020 play-in count is exactly one; each 2021–2026 play-in
   count is exactly six.

Approximate series-count bounds are not acceptance evidence. Exact published
results replace them.

## Raw play-by-play cache

Each exact `PlayByPlayV3` response and sidecar lives at:

```text
data/raw/stats_nba/pbp/games/<season>/<game_id>.json
data/raw/stats_nba/pbp/games/<season>/<game_id>.json.meta.json
```

The JSON body is transport-validated and published before tabular
normalization through the repository's checksummed cache helper. Its sidecar
records:

- provider and endpoint;
- exact request parameters;
- ending season and season label;
- game type and game ID;
- fetch timestamp, content length, and body SHA-256.

A cached response is transport-valid only when its body checksum, JSON
envelope, and every identity field agree with the worklist. Fetch-time
validation requires the expected outer game ID and a nonempty list of action
objects, but deliberately does not require the fixed action-field schema.
That schema is a publication contract: after publishing the raw pair, the
fetcher invokes the production parser and stops on schema drift while
retaining the exact response for review.

A missing half, identity mismatch, checksum failure, stale `.part`, malformed
JSON, wrong outer game ID, or empty action list stops the run. Verified cache
pairs are never silently overwritten or re-fetched. A transport-valid pair
with schema drift remains reusable raw evidence but continues to block the
build until the reviewed schema and fixtures are updated.

Before each network batch, `preflight_dns()` rejects empty, unspecified, or
loopback answers for `stats.nba.com`. A failed preflight performs no source
request; rerunning after resolver state is corrected is safe.

### Request discipline

- Requests are serialized with no parallelism.
- Request starts are at least 1.5 seconds apart.
- A transient network exception, HTTP 429, or HTTP 5xx receives at most five
  total attempts.
- Retry delays before attempts 2–5 are 5, 10, 20, and 40 seconds.
- A numeric `Retry-After` replaces the computed delay when it is larger and at
  most 120 seconds. A larger value stops the run for later resumption.
- Other HTTP 4xx responses, malformed payloads, and schema drift fail
  immediately.

The failure names the season, game type, game ID, attempt count, and exception
class. Completed pairs remain valid, so the next invocation resumes at the
first missing game.

## Capacity gate

The design was reviewed with approximately 477 GiB available on `/home` and
3.42 TB available on the mounted NAS. Those figures are observations, not
permanent assumptions.

After constructing the exact worklist, the fetcher remeasures the filesystem
in bytes and requires:

```text
available_local_bytes >=
    (uncached_game_count × 1,048,576) + 10,737,418,240
```

The one-MiB-per-game allowance is conservative relative to the 192–301 KiB
representative responses. The additional 10 GiB covers Parquet staging and
temporary publication. Archive and restore remeasure their destination and
require:

```text
destination_available_bytes >=
    source_allocated_bytes + (destination_total_bytes × 0.20)
```

No Windows NTFS partition or unallocated raw space is part of this plan.

## Parquet publication

The published tree is:

```text
data/parquet-large/pbp/
    _manifest.json
    season=1997/events.parquet
    ...
    season=2026/events.parquet
```

`data/parquet-large/` is gitignored and protected by repository-layout tests.
Each partition contains its ending-season column and is sorted by
`game_id, action_id`. `build-pbp` stages all 30 partitions and the manifest as
one tree, validates the stage, and then uses transactional tree publication.
Failure leaves the previous complete tree in place or retains a complete
rollback tree with an actionable path.

### Fixed event schema

The table preserves the outer game ID and every reviewed V3 action field.
Source score strings receive `_raw` names so they cannot be mistaken for the
derived running scores.

| Column | Arrow type | Contract |
|---|---|---|
| `game_id` | `large_string` | non-null outer V3 game ID |
| `action_id` | `int64` | non-null event identity and order |
| `action_number` | `int64` | non-null source value; duplicates allowed |
| `season` | `int64` | non-null ending season |
| `game_type` | `large_string` | `regular`/`playoff`/`play_in` |
| `clock` | `large_string` | non-null source ISO-8601 duration |
| `clock_seconds` | `double` | parsed seconds remaining |
| `period` | `int64` | non-null; 1–4 regulation, 5+ overtime |
| `team_id` | `int64` nullable | source value; zero is preserved |
| `team_tricode` | `large_string` nullable | source value; blank is preserved |
| `person_id` | `int64` nullable | source value; zero is preserved |
| `player_name` | `large_string` nullable | source value |
| `player_name_i` | `large_string` nullable | source value |
| `x_legacy` | `int64` nullable | source coordinate |
| `y_legacy` | `int64` nullable | source coordinate |
| `shot_distance` | `int64` nullable | source value |
| `shot_result` | `large_string` nullable | source vocabulary |
| `is_field_goal` | `int64` nullable | source 0/1 value |
| `shot_value` | `int64` nullable | source value |
| `score_home_raw` | `large_string` | exact source score string |
| `score_away_raw` | `large_string` | exact source score string |
| `score_home` | `int64` | non-null derived running score |
| `score_away` | `int64` | non-null derived running score |
| `points_total` | `int64` nullable | source value |
| `location` | `large_string` nullable | source vocabulary |
| `description` | `large_string` nullable | source text preserved verbatim |
| `action_type` | `large_string` nullable | source vocabulary |
| `sub_type` | `large_string` nullable | source vocabulary |
| `video_available` | `int64` nullable | source 0/1 value |

All 23 reviewed action keys must be present. An additional or missing key is
treated as upstream schema drift and stops parsing after the transport-valid
raw body is cached. Schema changes require an explicit design and fixture
update rather than silently widening or truncating the table.

### Clock normalization

`clock_seconds` parses the V3 `PT<minutes>M<seconds>S` value without replacing
`clock`. It accepts fractional seconds, including `PT11M35.00S`,
`PT00M07.30S`, and zero. Regulation clocks must lie within 0–720 seconds and
overtime clocks within 0–300 seconds.

### Running-score normalization

Events are traversed in strictly increasing `action_id` order:

1. Both raw score strings must be empty or both must parse as nonnegative
   integers. A one-sided blank or invalid value fails.
2. Before any nonzero score, numeric `0`/`0` establishes the initial state.
3. After scoring has begun, a raw `0`/`0` pair is the verified early-era
   missing-value sentinel and does not replace the current state.
4. An empty pair carries the current state forward.
5. Any other numeric pair becomes the new state, even when a legitimate score
   correction decreases one side.
6. Every row receives non-null derived `score_home` and `score_away`.

The first valid state must be 0–0. The final derived pair must equal the
worklist's home and away scores.

## Build and manifest gates

The complete offline build fails unless:

1. the raw worklist and game inventories contain exactly the expected regular
   files and complete body/sidecar pairs, with no orphans or unreferenced
   entries;
2. every worklist game has one nonempty response whose outer game ID matches;
3. each action has the exact source fields and source-compatible scalar types;
4. `action_id` values are positive, unique within the game, and strictly
   increasing in response order;
5. periods are contiguous from 1 and each clock is valid for its period;
6. every game has a terminal score equal to the worklist;
7. `(game_id, action_id)` is globally unique;
8. every event's season and type agree with its worklist row;
9. all 30 partitions exist, contain only their named season, and use the exact
   schema and deterministic ordering;
10. partition game sets equal the worklist in both directions; and
11. two consecutive builds from the same verified cache produce byte-identical
    partitions and `_manifest.json`.

Event counts are not constrained by an arbitrary 300–1,000 interval. A
nonempty structurally complete response with the correct terminal score is
accepted. Per-game and per-season counts, minima, maxima, percentiles, and
outliers are recorded for review.

The deterministic manifest contains:

- manifest format version and archive scope;
- exact logical schema and column order;
- dependency versions;
- every worklist body and sidecar relative path and SHA-256;
- every game body and sidecar relative path and SHA-256;
- exact normalized worklist counts by season and type;
- event and game counts by season and type;
- period and event-count distributions;
- each partition's row count, game count, byte size, and SHA-256;
- every validation-gate result; and
- deterministic per-season row hashes.

Absolute checkout paths, build timestamps, and other machine-specific values
do not enter the manifest.

## Audit report

A generated Markdown report is committed to
`docs/audits/2026-07-31-play-by-play-archive.md`. It summarizes:

- source-spike identities, response sizes, event counts, and terminal scores;
- worklist counts and exact cross-source equality;
- cache completion and validation;
- per-season games, events, periods, and event-count distributions;
- action-field availability and early-era score-sentinel usage;
- partition and manifest hashes;
- every build gate; and
- immutable NAS snapshot identity and restore verification.

The report is generated offline from the verified cache and deterministic
manifest. It does not become a second source of truth.

## Archival and recovery

The complete cache and publication form one recovery unit under:

```text
/mnt/nas/llm/documents/nba-predictions-archive/
    pbp-archive-2026-<manifest-sha12>/
        raw/stats_nba/pbp/
        parquet-large/pbp/
        SHA256SUMS
```

`archive_pbp_snapshot.sh`:

1. requires the trusted local manifest and complete validated inventories;
2. measures source allocation and NAS byte headroom;
3. stages only the PBP raw and publication trees;
4. rejects symlinks, special files, orphan pairs, stale parts, and
   unmanifested files;
5. writes a sorted checksum inventory for every regular file;
6. revalidates the source, stage, manifest binding, and checksum dry run; and
7. atomically publishes the immutable snapshot name.

If the same name already exists, it is accepted only when its complete content
is identical. Different content at an existing immutable name fails.

`restore_pbp_snapshot.sh`:

1. selects the snapshot by the trusted manifest SHA-256;
2. requires both raw and Parquet destinations to be absent;
3. validates the snapshot structure, manifest, and complete checksum
   inventory before copying;
4. stages both trees on their destination filesystem;
5. revalidates the snapshot and both stages;
6. validates the staged raw cache, performs a complete offline build in a
   separate verification location, and byte-compares that rebuilt publication
   with the staged publication;
7. publishes neither destination unless both stages and the rebuilt
   publication agree; and
8. publishes both with rollback protection, then rechecks their manifest and
   complete inventories.

Restore never overwrites a live cache or publication.

## Tests and execution gates

Committed fixtures are small, deterministic extracts based on the four
representative game IDs. Unit tests never access the network. They cover:

- exact action-key and scalar-type contracts;
- duplicate and non-monotonic `action_number`;
- unique, ordered `action_id`;
- historical `0`/`0` sentinels and modern blank scores;
- legitimate score corrections;
- regulation, fractional, zero, and overtime clocks;
- unknown ID prefixes and season-type disagreement;
- incomplete two-team worklist games;
- regular and postseason cross-source mismatches;
- the one-game 2020 and six-game 2021+ play-in rules;
- wrong outer game ID, empty actions, malformed JSON, and metadata tampering;
- duplicate/out-of-order action IDs, period gaps, and terminal-score mismatch;
- exact schema, partition membership, and deterministic rebuilds; and
- archive/restore inverses, tampering, races, incomplete pairs, unreferenced
  files, symlinks, special files, headroom failure, and existing targets.

Integration tests are explicitly marked and consume only checksum-valid local
caches. Before the bulk fetch, the four representative live responses must
pass the same production validators. After acquisition, two full offline
builds must match byte-for-byte before the snapshot is created.

## Out of scope

- Pace, clutch, foul-timing, scoring-run, timeout, or garbage-time features.
- Pre-1996 play-by-play, preseason, All-Star, exhibitions, tiebreakers, and
  voided games.
- Live or in-progress season ingestion.
- A dynamically widening Parquet schema.
- Any committed raw response or large Parquet artifact.
- Changes to existing regular-season or playoff publication rows.

## Success criteria

1. The exact cross-validated worklist covers every scoped game in ending
   seasons 1997–2026.
2. Every worklist game has one checksum-valid raw response and one or more
   validated event rows.
3. Every event is uniquely identified by `(game_id, action_id)`, all periods
   and clocks are structurally valid, and every terminal score matches.
4. The 30 deterministic season partitions and manifest rebuild
   byte-for-byte.
5. The committed audit records complete coverage, early-era source behavior,
   partition hashes, and all green gates.
6. The immutable NAS snapshot validates and restores both the raw cache and
   publication exactly without touching the live trees.
7. The repository's fresh-clone size remains below 100 MB because all large
   artifacts remain gitignored.
